# 12. ФИНАНСОВЫЕ ИНВАРИАНТЫ

Система обязана сохранять следующие правила:

1. Деньги не возникают без подтверждённой бухгалтерской операции.
2. Деньги не исчезают без учтённого списания.
3. Доступный баланс не может стать отрицательным.
4. Зарезервированный баланс нельзя потратить.
5. Один депозит нельзя зачислить дважды.
6. Один вывод нельзя выполнить дважды.
7. Покупка не может частично изменить внутреннего владельца без финансовой записи.
8. Комиссия рассчитывается по зафиксированной версии тарифа.
9. Историю проведённых операций нельзя произвольно переписать.
10. Любая корректировка проводится компенсирующей записью.

Добавь финансовые проверки при завершении транзакции.

При обнаружении расхождения:

- Зафиксировать инцидент.
- Приостановить затронутые операции.
- Уведомить администратора.
- Запустить reconciliation.
- Сохранить доказательства расхождения.

Не исправлять баланс обычным UPDATE.

# 13. CONCURRENCY ENGINE

Проверь конкурентные сценарии PostgreSQL.

Обязательные тесты:

- Два пользователя покупают один подарок.
- Один пользователь одновременно покупает несколько подарков на недостаточный баланс.
- Один подарок одновременно продаётся и выводится.
- Один оффер принимается несколькими продавцами.
- Одновременно выполняются отмена оффера и его принятие.
- Одновременно выполняются вывод средств и покупка.
- Цена изменяется во время покупки.
- Один подарок добавляется в два набора.
- Одновременно принимаются два Swap-предложения с одним подарком.

Использовать детерминированный порядок блокировки строк.

Обрабатывать deadlocks.

Повторять только безопасные идемпотентные операции.

Добавить тесты с несколькими независимыми соединениями PostgreSQL.

SQLite-тесты не считаются достаточным доказательством корректной конкурентной работы PostgreSQL.

TON Proof отсутствует в текущей версии.

Это критическая задача.

Изучи актуальную официальную документацию TON Connect и проверенные реализации серверной верификации.

Создай:

    packages/blockchain/ton-proof/
      challenge-service
      proof-verifier
      wallet-resolver
      domain-validator
      network-validator
      replay-protection

API:

    POST /api/v1/wallet/proof/challenge
    POST /api/v1/wallet/proof/verify
    GET /api/v1/wallet/connection
    DELETE /api/v1/wallet/connection

Сценарий:

1. Авторизованный пользователь запрашивает challenge.
2. Сервер генерирует криптографически случайный одноразовый nonce.
3. Challenge связывается с пользователем и сессией.
4. Кошелёк формирует TON Proof.
5. Backend проверяет подпись и все необходимые поля.
6. Backend подтверждает соответствие адреса кошелька публичному ключу.
7. Challenge атомарно помечается использованным.
8. Кошелёк привязывается к аккаунту.

Проверять:

- Domain.
- Timestamp.
- Nonce.
- Signature.
- Wallet Address.
- Wallet State Init.
- Public Key.
- Network Context.
- Session Binding.

Не доверять публичному ключу, если его соответствие адресу кошелька не подтверждено.

Не изобретать собственную криптографию.

Тесты:

- Валидная подпись.
- Неверная подпись.
- Подмена домена.
- Подмена адреса.
- Подмена ключа.
- Просроченный challenge.
- Повторное использование.
- Challenge другого пользователя.
- Неподдерживаемая сеть.

Использовать официальные или воспроизводимые тестовые векторы.

Отдельно проверить настоящий кошелёк после настройки HTTPS.
